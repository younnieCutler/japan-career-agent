# Career Agent GUI requirement trace

This trace is the strict acceptance record for the local GUI product work. It groups related
requirements without weakening them. The product sequence is **Capture → Review → Confirm →
Reuse**, and Career Vault remains the trusted shared core.

## Lifecycle invariants

| Subject | Invariant | Invalid transition that is rejected |
|---|---|---|
| Draft | Entered or autosaved input is never labelled approved and never mutates canonical state. Every mutation carries the revision it read. | A stale host saving over a newer draft; saving after completion or archive. |
| Workflow | One host-neutral APPLICATION record is discoverable by human context from GUI, CLI, Claude, and Codex. It contains semantic continuation state, not transcripts or host session memory. | Proposing an unplaced experience; silently choosing among several matching workflows. |
| Self-analysis | The shared workflow uses the existing reviewed profile shape. Hypotheses, reviewed empty values, and Unknown remain distinct until explicit approval. | Approving without a reviewable profile; replacing a newer cross-entrypoint revision. |
| Proposal | A pending proposal is a review snapshot bound to one draft revision, not canonical truth. Re-submitting after an edit atomically refreshes that pending snapshot and advances the shared revision; an older screen cannot approve it. | Approving a snapshot after its draft changed; rebinding a proposal to another case. |
| Approval | The user sees the exact after-state, Unknowns, evidence, effect, and meaningful before/after change immediately before approval. The committed event is the reviewed snapshot plus approved lifecycle state. Retry is idempotent. | Generic approval bypassing the session snapshot; numeric claims without numeric support; approval after archive. |
| Career context | Employer, freelance work, personal activity, education, volunteer work, and other activity are explicit contexts. Employment and non-employment semantics are derived from kind, not from whether a company exists. | Using a target-company application record as career history; changing a confirmed context chain implicitly. |
| Project | Every new project has one active, approved career-context parent. A confirmed project remains anchored to that context. Legacy parentless projects stay readable but require explicit repair before new work. | Creating under an archived/unconfirmed/wrong-kind parent; repairing under the wrong confirmed context. |
| Application | Target-company/application records are separate from employer career history. Only user-selected, externally usable approved experience evidence flows to an application document. Documents inherit that selection without exposing references. | Attaching a document to a non-application or inactive case; silently reusing blocked/review-required confidential evidence. |
| Human judgment | Consequential application decisions are L3 by server-owned deterministic policy. The human initial view is durable before Agent advice is revealed; Agent advice, human final judgment, and later outcome are separate append-only phases and never career evidence. | Client-selected impact downgrade; Agent phase before human initial; duplicate/out-of-order phases; fabricated Agent recommendation; raw unresolved evidence refs rendered as evidence. |
| Canonical facts | Only the approval owner appends canonical facts. Unknown remains Unknown, qualitative outcomes need no invented metric, and user confirmation is not material numeric evidence. Cases and artifacts are organizing metadata, never evidence by themselves. | Treating a populated field, case, artifact, or heartbeat acknowledgement as confirmed career truth. |
| Archive/recovery | Archive is explicit, consequence-labelled, CAS-protected, and recoverable. Confirmed history is not casually archived or deleted. | Archiving a parent with active children; stale archive/restore; hiding confirmed history through organizer metadata. |

## Messy-user and adversarial matrix

The regression suite actively covers duplicate contexts/projects, multiple unfinished workflows,
wrong or archived parents, personal/education/freelance contexts, partial/current/unknown periods,
qualitative and not-measured outcomes, confidential evidence, stale hosts, interrupted checkpoints,
stale proposals, archive/recovery, hand-edited documents, rejected approval, idempotent retry, and
language switching with unsaved work. These cases are not represented as a separate demo mode; they
exercise the production owners and projections.

## Rendered-QA limitation

The 2026-08-13 rendered pass successfully covered the NEW state and an ACTIVE end-to-end context,
project, qualitative experience, review, approval, confidentiality/evidence, application, keyboard,
and 320px responsive journey with no observed console error or page overflow. In the current
execution sandbox, a fresh loopback bind fails with `PermissionError: [Errno 1] Operation not
permitted`, and Chromium aborts while creating its Mach rendezvous port. Therefore the latest
incremental controls and HEAVY state are verified by HTTP/DOM/localization contracts and production
read-model tests rather than claimed as freshly rendered. This is an external verification
constraint, not a relaxed product invariant; the process E2E test is mandatory when loopback is
available.
